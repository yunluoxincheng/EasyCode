## 测量口径

- 请求开始、响应可用和流首块由同一页面的 `performance.now()` 记录。首个数据块可能只是协议状态，不能称为首 Token；请求/流耗时包含网关、上游服务、传输及客户端消费，不能全部归因于模型计算。
- 引擎事件来自真实 AgentClient；DOM 时间由 MutationObserver 记录，表示 DOM 提交，不是屏幕实际绘制。没有保存 SSE 内容，只统计时间、字节数、事件类型及长度。
- 第一次 `edit_file` 的既有 `durationMs=30,949` 包含约 30,867ms 审批等待；不能把卡片总耗时当作纯文件写入时间。扣除审批后的工具路径仍包含守卫、快照和通知等开销。
- 第一次的 77/58ms 长任务发生在发起早期，63ms 发生在收尾；正文增量期间未观察到 >=50ms 的长任务。首次会话挂载附近另有 197ms 长任务，开始于本次发送前，未计入活动期表格。
- 两次的审批方式、缓存状态和上游响应均不同，50.626s 与 16.487s 不能作为优化前后对照。两次小任务也不足以推断长会话、长 Markdown 或其它模型的性能。

## 定位结论与后续候选

本次正文事件到 DOM 的延迟较短，没有发现正文渲染积压。扣除审批后，大部分时间位于请求与流消费阶段，暂无依据继续改写解析/渲染机制。

两个工具回合均没有正文或推理文本增量，界面保留通用运行提示。Responses 适配器在 `response.completed` 后才构造最终工具调用，执行及审批事件随后发生。后续可利用真实流事件区分“生成工具调用”“等待审批”“实际执行”，并拆解耗时口径；首数据块不等于工具名已可确定，不能把未完成参数当作可执行调用。该基线阶段未改动生产路径，后续实施见下节及 TODOS #64。

## 2026-10-20：工具阶段提示与耗时分段

真实网关的元数据探测确认 `response.output_item.added` 包含 function_call/name/call_id，早于完成事件，参数增量仍在继续。适配器据此每个调用仅发一次生成事件，不传参数。完整调用仍来自完成响应，审批及执行时点保持原有顺序。执行开始事件从工具守卫与工作区锁之后的实际入口发出。

隔离 Windows Tauri 中，gpt-6.1-sol 实际编码任务记录到以下顺序：生成调用 → 完整调用/检查 → 等待审批 → 检查/排队 → 实际执行 → 结果。一次编辑的生成提示在发送后约 8.778s 显示，完整调用在 11.982s 确认，提前约 3.2 秒提供了阶段反馈；这不是模型响应或任务完成提速。

| 真实调用场景 | 总耗时 | 审批 | 执行 | 检查/排队 | 结果 |
|---|---:|---:|---:|---:|---|
| 拒绝编辑（最终构建复核） | 1528ms | 1510ms | 未执行 | 18ms | 文件不变，无执行开始事件 |
| 批准后等待工作区锁 | 2771ms | 1509ms | 45ms | 1217ms | 解锁后执行并完成 |
| `node --version` | 2434ms | 1205ms | 1229ms | 0ms | 真实进程返回成功，终端卡片分段显示 |

排队场景中，在批准后继续持有真实工作区锁约 1.2 秒；锁释放前 UI 显示“正在检查并等待执行”，没有执行开始事件，目标文件也未变化。最终拒绝场景卡片显示“未执行 · 审批 1510ms”。工具结果中的执行耗时缺省表示未运行，0 表示已运行但不足 1ms，显示不依赖 UI 是否收到执行开始事件。

停止场景在约 3.683s 收到生成事件，3.698s 以 aborted 收敛，无模型工具执行，生成状态和 ticker 均清除。停止后的迟到生成事件回放被忽略。删除真实工具记录的可选 timing 字段做兼容回放时，只显示“总 2771ms”，不补造执行/审批数据。真实终端截图也核对了卡片布局。

Core、engine 编译、UI 类型、工作区构建和 Tauri 原生构建通过，71 项现有聚焦检查通过，未增加测试文件或依赖。另用真实 NodeHost 文件与审批路径核对最终计时契约：拒绝无执行字段和执行开始回调，批准后才产生执行字段。GUI 证据仅覆盖 Windows Tauri，远端结果以本分支 PR Checks 为准，未验证其它模型协议的生成提示；其它协议仍沿用通用等待提示，工具审批/执行计时通路共用。
