### 20. 输入控制体验打磨：Composer 自适应高度 + 顶部栏响应式收敛 + 文件拖拽填充

**状态**：已记录，未排期

**背景**：
1. **输入框固定高度局促**：Composer 输入框目前固定为 `rows={3}`，输入多行 Prompt 或粘贴长配置/代码片段时高度不会自动变化，只能在内部上下滚动，缺乏现代编辑器的平滑手感。
2. **顶部状态栏（Composer Bar）横向易拥挤**：顶部并排堆叠了审批模式、工作区选择、模型选择、Token 用量、上下文容量等多个状态控件，在窗口较窄或侧栏展开时容易发生挤压、折行或内容溢出。
3. **缺乏文件拖拽交互**：用户需要引用外部文件时，目前必须手动在外部复制绝对路径并粘贴。

**期望行为**：
1. **输入框自适应撑高（Auto-grow Textarea）**：输入多行时根据文字内容平滑自适应高度（2 行 ~ 8 行自增），超过 8 行后再出纵向滚动条，发送后自动收缩回初始高度。
2. **顶部工具栏响应式收敛**：在窗口可用宽度紧张时，次要信息（如具体的 Token 用量 / 上下文容量）自动收敛为微型图标或进度环，鼠标悬停时（Tooltip）浮出详细看板，优先保障模式切换与模型选择的完整可见性。
3. **文件拖拽填充（Drag & Drop）**：支持直接从系统文件管理器将文件或文件夹拖放至输入框内，自动获取其路径并填入当前光标位置。

**涉及改动**：
- `packages/ui/src/components/Composer.tsx`（自适应高度 Hook、拖放 drop 事件监听）
- `packages/ui/src/styles.css`（Composer 响应式布局自适应与拖拽悬停高亮态）

### 21. 运行态与终端拟态强化：Agent 实时动作指示器（Live Ticker）+ run_command 拟终端卡片

**状态**：已记录，未排期

**背景**：
1. **运行中缺少当前步骤感知**：当 Agent 在执行长链路任务（如大文件检索、复杂 Shell 脚本执行、联网搜索）时，界面仅有右上角与回合头部的呼吸点，用户无法感知 Agent 正在执行哪一个动作、当前动作已耗时多久，容易产生“卡死”或等待焦虑。
2. **run_command 缺少终端沉浸感**：目前命令执行的输出只是一个普通 kv 文本框，文字输出扁平，缺乏终端命令执行的拟物感与 ANSI 颜色支持。

**期望行为**：
1. **实时动作指示器（Live Action Ticker）**：
   - Agent 运行时，在当前正在活动的回合底部或输入区上方常驻展示一条动态瞬态状态行；
   - 示例：`❯ [run_command] 正在执行: pnpm test ... (已耗时 2.4s) █`；随着每个工具的开始与完成即时刷新，大幅消除等待焦虑。
2. **run_command 拟终端卡片**：
   - 工具卡片展开后呈现仿终端控制台窗口样式（顶部带 `$ 命令` 标题条）；
   - 支持基础 ANSI 颜色转码高亮（例如测试通过的绿字、报错的红字），执行中带呼吸光标，完成后标明执行状态码（exitCode）。

**涉及改动**：
- `packages/ui/src/store.ts`（记录当前瞬态活跃的 toolCall 与计时状态）
- `packages/ui/src/components/Transcript.tsx`（新增 Live Ticker 状态条、run_command 卡片拟终端化渲染、轻量 ANSI 解码）
- `packages/ui/src/styles.css`（拟终端视窗样式、ANSI 经典色系变量、终端光标闪烁动画）

### 18. 会话视口重构：模型过程独立滚动视窗 + 任务清单常驻吸顶

**状态**：已记录，未排期

**背景**：
1. **消息容易被推走**：目前会话界面为全局单一瀑布流滚动容器（`.transcript-scroll`）。当用户发出指令后，模型在执行多步骤复杂任务时会产生大量思考过程、工具调用卡片（读文件、搜索、编辑、跑命令等）和日志流输出，持续触发主视口贴底滚动，导致用户的上一条提问以及上下文历史被迅速顶出视口几十屏开外，用户失去了对提问上下文的对照与掌控感。
2. **计划清单容易被淹没**：目前 `todo_write` 工具生成的 `TodoCard` 混在工具流中，当模型后续继续调用多次其他工具或输出大量文本时，计划清单会被冲到上面；用户在执行过程中无法直观了解全局进度和当前执行步骤。

**期望行为**：
1. **模型过程独立滚动视窗（形态 A）**：
   - 回合展开态（`TurnView`）的过程体（`turn-body`，包括思考过程、工具调用卡片、过程说明等）设为局部独立滚动视窗，设定最大高度约束（如 `max-height: 55vh` 或视口自适应），开启 `overflow-y: auto`。
   - 模型流式输出与工具执行期间，自动贴底跟随仅发生在回合内部的局部视窗内，外层主会话区域不再疯狂下滚，用户的 Prompt（`UserView`）始终平稳停留在上方可视区域内。
   - 回合完成或折叠后仍沿用原折叠逻辑，只保留最终结果与统计，保持界面整洁。
2. **任务清单顶部常驻吸顶（Sticky Header）**：
   - 计划清单从滚动的消息流中抽离，作为常驻组件吸顶固定在 `Transcript` 会话可视区顶部（或时间线刻度旁）。
   - **收折/紧凑态（默认）**：展示单行极客风状态栏，如 `[◍ 进度 3/5 · 60%] 正在进行: 修复 styles.css 滚动样式 ▾`。
   - **展开态**：点击可向下展开完整的 TodoCard 面板，查看每一项步骤的详细状态（待办/进行中/完成）与优先级。
   - 若会话中无 Todo，则自动隐藏，不占空间。

**实现要点**：
- **数据流就绪**：UI store 中已维护全局响应式状态 `store.activeTodos`，直接供顶部常驻条订阅。
- **滚动逻辑解耦**：
  - 外层 `transcript-scroll` 仅在用户发送新消息（`scrollTick`）或切换会话时贴底定位到当前用户消息；
  - 过程输出流式事件仅触发当前活动 Turn 的局部视窗贴底，与外层滚动隔离，防止外层被联动拉扯。
- **样式与高度计算**：`.turn-body` 设置独立滚动条与自适应视高，注意与左侧时间线轨道（`rail`）的刻度锚点计算（`measure` / `data-anchor`）保持协调。

**涉及改动**：
- `packages/ui/src/components/Transcript.tsx`：新增顶部 Sticky Todo 组件；修改 TurnView 的 `turn-body` 滚动容器与局部滚动 ref；滚动监听与解耦。
- `packages/ui/src/styles.css`：顶部吸顶 Todo 栏样式；`.turn-body` 局部滚动容器与最大高度样式。

### 13. 任务完成桌面通知（右下角，应用风格）

**状态**：✅ 已完成（2026-09-20 随 v0.1.8 实现；2026-09-21 随 v0.1.9 补齐子项）

**已实现**：
- 走系统原生通知（Rust 命令 `send_notification`），经 AgentClient 抽象：Tauri 用系统通知、Electron 用主进程 `Notification`、演示模式退回浏览器 Web Notification
- 触发时机：store 的 `done` 事件（Agent 回合结束），且 `document.hasFocus()` 为假（窗口在后台）才发；前台时沿用应用内 toast，不重复打扰
- 文案区分：回合内出现过错误条目（loop 保证 error 后必发 done，不会双发）→「EasyCode — 任务出错」，否则「EasyCode — Agent 完成」，正文为会话标题
- **点击唤起**（Windows）：winrt toast 挂 `on_activated` 回调，点击通知 → 主窗口 unminimize + show + set_focus；非 Windows 走插件无点击回调
- **设置开关**：设置页「常规」→「任务完成桌面通知」（`settings.desktopNotify`，默认开）

**已知行为：dev 构建的通知会署名为「Windows PowerShell」**（图标也是 PowerShell 的），这是插件的刻意设计而非缺陷：`tauri-plugin-notification` 的 Windows 分支检测到 exe 位于 `…/target/debug` 或 `…/target/release` 时**不设置 `System.AppUserModel.ID`**（源码注释：*set the notification's System.AppUserModel.ID only when running the installed app*），于是 `tauri-winrt-notification` 落到它文档化的兜底方案 `Toast::POWERSHELL_APP_ID`（该常量注释原文：*the toast will erroneously report its origin as powershell*）。v0.1.9 起 Windows 直连 winrt toast，沿用同一策略（dev 回退 PowerShell AUMID，否则 toast 拒发）。

**安装版（NSIS）署名正常**：包外路径运行时会传 `app_id = com.easycode.desktop`，且该 AUMID 已由安装器的开始菜单快捷方式注册（`EasyCode.lnk` 的 `System.AppUserModel.ID` 属性即此值）。实测对比：debug 路径运行 → 通知库里 `powershell.exe` 计数 +1；把 exe 复制到非 `target` 路径运行 → `com.easycode.desktop` 计数 +1。**因此验收通知署名需用安装版，不要在 dev 构建下按此判缺陷。**

**设计取舍**：自绘终端风小窗（原方案 b）不做——系统通知已覆盖提醒诉求，且与「点击唤起」天然配合；若未来要与应用风格完全一致再评估。

### 2. 编辑加固：edit_file 强制"先读后改"

**状态**：✅ 已实现（2026-09-20，随 v0.1.7）——回合内维护已读文件集合，edit_file / 覆盖已有文件的 write_file 未读即拒绝并引导先读；edit/write 成功后也记入集合（会话内改过的文件可直接再改）

**背景**：当前 `edit_file` 不校验该会话是否读过目标文件，唯一防线是 `old_string` 精确匹配且唯一。模型理论上可以凭猜测"盲改"（碰巧匹配到通用代码片段），造成误改。

**业界参考**：Claude Code 等 Agent 对编辑类工具有硬约束——未在当前会话中读过的文件，编辑请求直接拒绝并提示先读。

**方案**（讨论中倾向）：
- 会话运行时维护"已读文件集合"（read_file 成功执行后记录绝对路径）
- `edit_file` / `write_file`（覆盖已有文件时）执行前检查：目标不在集合中 → 拒绝执行，返回"请先 read_file 该文件"引导模型补读
- 新文件（write_file 创建）不受限制
- 代价：个别场景多一轮读取；收益：消灭盲改类误操作

**涉及改动**：core 工具层（需要跨工具调用的会话内状态，ToolContext 传递或 AgentServer 维护）。
